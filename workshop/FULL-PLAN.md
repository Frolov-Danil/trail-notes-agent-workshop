# Trail Notes — повний план практикуму

## Мета й результат

Один учасник керує двома AI-агентами у двох окремих чатах і worktree:
перший робить редизайн за Figma через MCP, другий додає офлайн-читання.
Після перевірки обох задач учасник локально об’єднує зміни та демонструє
оновлений застосунок зі збереженими матеріалами без доступного API.

Тривалість зустрічі — 90 хвилин. Інструменти й доступи налаштовуємо заздалегідь.
Учасник сам керує агентами; ведучий спостерігає та допомагає запитаннями.
Результати залишаються на комп’ютері учасника. Push і pull request не потрібні.

## 2. Що ведучий готує до першої зустрічі

- Опублікувати стартовий проєкт і тег `workshop-v1`, перевірити свіжий клон.
- Надати учасникам доступ до приватного репозиторію за їхніми GitHub-логінами.
- Надати доступ до Figma-файлу й перевірити читання макета через MCP учасника.
- Надіслати розділи 3–4 цього плану щонайменше за день до зустрічі.
- Перевірити, що учасник може працювати у двох чатах агента.
- Підготувати коротку демонстрацію: бібліотека, стаття, помилка після зупинки API.
- Не використовувати для вправи робочий репозиторій компанії.
- Фіксувати спостереження за однаковими критеріями з розділу 13.

## 3. Що учасник встановлює заздалегідь

1. Git і доступ до GitHub через SSH або HTTPS.
2. Node.js з `.nvmrc` — 22.13.0; npm; Python 3.
3. Звичний редактор та AI-агент для вправи.
4. Одну знайому мобільну платформу для основної перевірки:
   - iOS: macOS, Xcode, встановлений iOS Simulator.
   - Android: Android Studio, Android SDK, створений і запущений Android Emulator.
5. Expo Go, сумісний з Expo SDK 57. Якщо версія не підходить,
   перевірити https://expo.dev/go до зустрічі.
6. Figma MCP у своєму агенті, авторизований власним акаунтом.

На першій зустрічі не змушуємо iOS-розробника встановлювати Android SDK і навпаки.
Основний сценарій перевіряємо на його платформі, бандли експортуємо для обох.
Ведучий окремо перевіряє другу платформу перед наступними заняттями.
Вебперегляд допомагає з версткою, але не замінює мобільну перевірку.
Ключі API, паролі й токени до репозиторію не додаємо.

## 4. Завантажити проєкт і перевірити старт

Команди виконувати в Terminal. Якщо SSH не налаштовано, замість SSH-адреси
взяти HTTPS URL з кнопки Code на GitHub.

```sh
git clone git@github.com:Frolov-Danil/trail-notes-agent-workshop.git
cd trail-notes-agent-workshop
git fetch origin --tags
npm ci
```

Якщо встановлено nvm, перед `npm ci` можна виконати `nvm install` і `nvm use`.
Ведучий підтримує основну версію репозиторію як старт для вправи. Якщо вона
надалі зміниться, агент має підготувати свіжий локальний клон від `workshop-v1`,
зберігши окреме місце для локального об’єднання.

Термінал 1 з кореня проєкту:

```sh
npm run api
```

Термінал 2 з кореня проєкту:

```sh
npx expo start --port 8080
```

Натиснути `i` для iOS Simulator або `a` для Android Emulator.
Перевірити: є чотири матеріали, перший відкривається, повернення назад працює.
Зупинити API через Ctrl+C, натиснути «Обновить» й отримати помилку.
Знову запустити API, натиснути «Повторить» й отримати список.
Назви кнопок наведено так, як вони зараз відображаються у стартовому застосунку.

Перед роботою двох агентів зупинити цей Metro через Ctrl+C. API можна залишити.

| Де працює застосунок | Адреса API |
| --- | --- |
| iOS Simulator / браузер | `http://127.0.0.1:8765` |
| Android Emulator | `http://10.0.2.2:8765` |
| Фізичний телефон | LAN-IP комп’ютера, див. README |

Сервер працює на комп’ютері кожного учасника й входить до репозиторію.
Для першої вправи використовуємо симулятор/емулятор, щоб не витрачати час
на налаштування мережі фізичного телефона.

## 6. Підготувати два worktree

Кожен учасник працює у власному локальному клоні. Персональні назви гілок
не потрібні; нічого не публікуємо назад у GitHub.
Git використовує локальні гілки для worktree й створить їх автоматично.

У корені свіжого клону:

```sh
git worktree add ../trailnotes-redesign
git worktree add ../trailnotes-offline
git worktree list
```

Команди припускають, що ці папки й відповідні локальні worktree ще не існують.
Якщо вправа повторна, агент має перевірити стан попередньої спроби та
зберегти її зміни перед створенням нової копії.

```text
trail-notes-agent-workshop/     — початкова версія, API, потім об’єднання
trailnotes-redesign/            — агент A
trailnotes-offline/             — агент B
```

У кожній новій папці виконати `npm ci`.
Відкрити два окремі чати агента; робоча папка кожного має відповідати його worktree.
Два чати в одній папці не забезпечують ізоляції.

Перша дія агента — показати свою робочу папку та поточний стан Git,
прочитати `AGENTS.md` і відповідне завдання. Учасник перевіряє результат.

## 7. Поставити задачі агентам

### Агент A — редизайн

Промпт у чаті, відкритому в `trailnotes-redesign`:

> Працюємо з навчальним Trail Notes. Покажи поточну робочу папку та стан Git.
> Прочитай AGENTS.md і workshop/TASK-A-REDESIGN.md.
> Зроби редизайн бібліотеки й статті за посиланнями Figma із завдання.
> Спочатку перевір читання вузлів через Figma MCP, потім запропонуй короткий
> план, перелік файлів і критерії перевірки. Починай реалізацію після мого
> повідомлення «починай».
> Постійний кеш робить інший агент. Не змінюй контракт ArticleService та
> логіку useLibrary без узгодження. Працюй лише у своєму worktree.
> Не роби merge, push або pull request. Наприкінці покажи diff, результати
> перевірок і обмеження та створи локальний коміт.

### Агент B — офлайн

Промпт у чаті, відкритому в `trailnotes-offline`:

> Працюємо з навчальним Trail Notes. Покажи поточну робочу папку та стан Git.
> Прочитай AGENTS.md і workshop/TASK-B-OFFLINE.md.
> Додай постійний кеш статей і читання без доступного API за завданням.
> Спочатку запропонуй короткий план, перелік файлів і сценарії перевірки.
> Починай реалізацію після мого повідомлення «починай».
> Редизайн робить інший агент. Збережи поточне оформлення; зміни LibraryScreen
> обмеж підключенням стану та статусу. Узгодь зі мною поля стану для агента A.
> Працюй лише у своєму worktree. Не роби merge, push або pull request.
> Наприкінці покажи diff, перевірки й обмеження та створи локальний коміт.

Пауза після плану — навчальна контрольна точка: учасник має зрозуміти
запропоноване рішення, а не лише отримати готовий код.

## 8. Як працювати паралельно

### До реалізації: узгодити один спільний контракт

Учасник порівнює плани й передає кожному агенту короткий виклад плану іншого.
Агенти не бачать чужий чат автоматично.

| Частина проєкту | Основний відповідальний |
| --- | --- |
| LibraryScreen, ArticleScreen, візуальні компоненти | Агент A |
| articleService, useLibrary, сховище, тести кешу | Агент B |
| Поля стану для офлайн-банера та підключення в LibraryScreen | Узгодити до реалізації |
| Нові залежності | Кожен повідомляє учаснику; при об’єднанні зберегти всі потрібні |

Наприклад, узгодити `isOffline`, `lastUpdatedAt` і дію `refresh`.
Це приклад контракту, а не обов’язкова архітектура. Точні назви мають збігатися.
Задача A повинна збиратися окремо: банер можна оформити компонентом із props,
не підключаючи його до полів хука, яких ще немає у цій робочій копії.

Після узгодження учасник пише «починай» в обидва чати. Агенти виконують
задачі одночасно, кожен у своєму worktree.

### Під час роботи: коротка контрольна точка

Через 10–15 хвилин попросити в кожного:

> Що вже зроблено, які файли змінилися, чи є перетин із другою задачею?
> Назви одне рішення, яке мені потрібно перевірити.

Якщо агент вийшов за межі задачі, учасник уточнює рамки. Якщо змінився контракт,
передає точне оновлення іншому агенту. Постійно зливати незавершені зміни
між worktree не потрібно. Основне об’єднання — після перевірки двох результатів.

### Запуск двох версій

Основний клон тримає API на 8765. Для worktree використовуємо окремі Metro:

```sh
# Термінал у trailnotes-redesign
npx expo start --port 8081
```

```sh
# Термінал у trailnotes-offline
npx expo start --port 8082
```

Писати код можна одночасно, а перевіряти версії по черзі в одному симуляторі.
Для двох одночасно видимих результатів потрібні два пристрої.
Запускати потрібний проєкт із відповідного термінала Metro; перед перевіркою
звіряти папку й порт. В Expo Go відкривається конкретний проєкт із конкретного Metro.

Worktree ізолює файли та Git, але не порти, сервери й дані симулятора.
Зупинка спільного API впливає на обидві версії — домовитися про час перевірки.
Для незалежного API задачі B можна використати порт 8766 і `.env` з
EXPO_PUBLIC_API_URL, враховуючи адресу платформи з таблиці вище.

## 9. Перевірити кожен результат до об’єднання

У кожному worktree:

```sh
git status --short
git diff
npm run typecheck
npm test
npx expo export --platform ios --platform android --output-dir dist
```

Агент пояснює, що перевірив сам, а що треба перевірити вручну.
Учасник переглядає зміни й запускає застосунок на своїй мобільній платформі.

### Приймання A

- Обидва екрани відповідають Figma: структура, кольори, тексти й відступи.
- Картки відкривають правильну статтю; повернення до бібліотеки працює.
- Loading, error та empty стани залишилися доступними.
- Довгі заголовки й збільшений системний шрифт не приховують основний текст.
- Немає реалізації кешу чи необґрунтованої зміни архітектури.

### Приймання B

- Чотири матеріали та повний текст збережені на диску після успішного запиту.
- Python API зупинений, Metro працює.
- Проєкт повністю закрито й відкрито знову: список і стаття доступні з кешу.
- Є статус збережених даних і час останнього оновлення.
- Без кешу або з пошкодженим кешем є зрозуміла помилка й повторна спроба.
- Після запуску API оновлення завантажує актуальні дані та прибирає офлайн-статус.
- Невдалий запит не знищує добрий кеш; скасування не виглядає як помилка мережі.

Очищати лише ключі/файли Trail Notes. Не видаляти Expo Go та дані інших проєктів.
Режим польоту не є надійним способом вимкнення localhost API.
Успішний bundling сам по собі не доводить працездатність екранів.

Агенти створюють локальні коміти. Перед об’єднанням робочі дерева мають
бути чистими. Якщо залишилися незакомічені зміни — з’ясувати причину.

## 10. Локально об’єднати результати

Відкрити чат агента в основному клоні `trail-notes-agent-workshop`.
Учасник перевіряє, що це саме основна папка, а не один із двох worktree.

Промпт:

> Потрібно локально об’єднати два перевірені результати Trail Notes.
> Покажи робочу папку, git status і git worktree list --porcelain.
> Визнач локальні гілки worktree ../trailnotes-redesign та ../trailnotes-offline.
> Переконайся, що зміни обох закомічені, а основна папка чиста.
> У цій основній папці послідовно злий спочатку редизайн, потім офлайн,
> зберігши окремі merge-коміти. Не перемикай інші worktree та не роби push або PR.
> Якщо виникнуть конфлікти, поясни обидві версії та збережи новий дизайн,
> постійний кеш, повторне завантаження й офлайн-статус.
> Наприкінці виконай перевірки та покажи, як збережено обидва результати.

Злиття виконуємо послідовно. Якщо перше зупинилося на конфлікті,
друге не починати до його завершення.

Для перегляду конфліктів:

```sh
git status
git diff --name-only --diff-filter=U
```

У package.json спочатку узгодити сукупність потрібних залежностей,
потім коректно оновити package-lock.json через npm. Після об’єднання виконати
`npm ci` і `npx expo install --check`. Вибір однієї версії lockfile без
перевірки залежностей не є достатнім рішенням.

Git-конфліктів може не бути, а поведінка може зламатися — тому єдина версія
має окрему загальну перевірку.

## 11. Перевірити єдиний застосунок

В основному клоні після завершення merge:

```sh
npm ci
npm run typecheck
npm test
npx expo install --check
npx expo export --platform ios --platform android --output-dir dist
npx expo start --port 8083
```

Обов’язкова демонстрація:

1. API ввімкнений → новий дизайн бібліотеки → стаття → назад.
2. API вимкнений → оновлення → збережені матеріали та офлайн-статус.
3. Закрити й знову відкрити проєкт із вимкненим API → стаття читається.
4. API ввімкнений → оновлення → статус зникає, дані актуальні.
5. Очищений лише кеш Trail Notes, API вимкнений → зрозуміла помилка.
6. API ввімкнений → «Повторить» → застосунок знову працює.
7. Збільшений системний шрифт → основні тексти й дії доступні.

## 12. Що робити з результатом

Усі зміни залишаються локально. Ведучому достатньо демонстрації екрана,
пояснення diff і результатів перевірки. Історію локальних комітів можна
подивитися командою:

```sh
git log --oneline --graph --all -12
```

У GitHub нічого завантажувати не потрібно. Спільний стартовий репозиторій
залишається основою для інших учасників.

Після заняття зупинити Metro з робочих копій, перевірити чистоту дерев і
збереження результатів в основному клоні. За бажанням прибрати worktree:

```sh
git worktree remove ../trailnotes-redesign
git worktree remove ../trailnotes-offline
```

Коміти зберігаються локально. `--force` для прибирання не використовувати.

## 13. Як зрозуміти, що навчання спрацювало

Учасник може пояснити:

- Як поставити агенту задачу з перевірним результатом.
- Чому відповідь агента не замінює перевірку коду й застосунку.
- Як переконатися, що агенти працюють у різних папках.
- Де перетнулися задачі та як узгодили інтерфейс між ними.
- Як він помітив і виправив хоча б одну помилку чи спірне рішення агента.
- Що перевірив до merge та що додатково перевірив після нього.
- Як відрізнити постійний кеш від даних, які залишилися в пам’яті.

Ведучий для кожного пункту відзначає: «самостійно», «з підказкою», «не вдалося».
Швидкість генерації коду не є єдиним критерієм.

Після зустрічі — невелика задача у знайомому нативному проєкті:
поставити її агенту, обмежити scope, перевірити diff і показати результат.
Так перевіряємо перенесення навички з навчального React Native у щоденну роботу.

## 14. Типові проблеми

| Симптом | Що перевірити |
| --- | --- |
| GitHub: Repository not found | Акаунт і доступ до приватного репозиторію |
| MCP не бачить макет | Акаунт Figma, доступ до файлу й авторизацію MCP |
| API недоступний | Python запущений, правильна адреса платформи та порт |
| Expo Go не відкриває проєкт | Сумісність SDK 57, Metro й URL потрібного worktree |
| Відкривається стара SwiftUI-іконка | React Native проєкт запускати через Expo Go |
| Видно стару версію екрана | Перевірити папку й порт Metro |
| localhost не працює на macOS | `NODE_OPTIONS=--dns-result-order=ipv4first npx expo start --localhost --port 8081` |
| Порт зайнятий | Зупинити свій попередній сервер або вибрати інший порт |
| Зупинка API для B вплинула на A | Спільний API; узгодити час перевірки |
| Після merge застосунок не збирається | Перевірити об’єднані залежності й виконати npm ci |
| До перезапуску дані є, після — порожньо | Постійний кеш не підтверджений, дані були лише в пам’яті |

Обмеження залежностей та перевірки стартової версії:
`workshop/DEPENDENCIES.md` і `workshop/VERIFIED.md`.
